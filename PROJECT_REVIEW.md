**Highest-priority findings**

1. **Credentials are embedded in the supplied project.** An SMTP username/password appears in application configuration and Compose. Database passwords, fallback JWT signing secrets, and a documented initial admin password are also included. With the default JWT secret, someone who obtains the source can create tokens accepted by the server. Remove real secrets from source, require deployment secrets, and replace any credentials already used outside development. The SMTP password's validity was not tested. Also, Compose's `MAIL_USERNAME`/`MAIL_PASSWORD` variables are not referenced by the hardcoded `spring.mail` settings; changing those variables alone will not update the sender configuration. See [application.yml](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/resources/application.yml:20), [Compose](C:/Users/tapan/Desktop/bangla-karneval/docker-compose.yml), and [seed.sql](C:/Users/tapan/Desktop/bangla-karneval/database/seed.sql:1).

2. **Public contact submissions can inject attributes into the admin message view.** The shared `escapeHtml()` escapes text content but leaves quotation marks unchanged. `loadMessages()` places its output inside quoted `data-name` and `data-message` attributes. A submitted quotation mark can end an attribute and introduce an event handler, creating a stored cross-site scripting path when an admin interacts with the result. The admin token is stored in localStorage, increasing the impact. Build these elements with DOM APIs and assign `.textContent`/`.dataset` instead of interpolating user input into HTML. Related unsafe rendering exists in public event/sponsor cards and sponsor inline handlers; an ordinary apostrophe in a sponsor name also breaks the delete handler. See [common.js](C:/Users/tapan/Desktop/bangla-karneval/frontend/js/common.js:100), [admin_dashboard.js](C:/Users/tapan/Desktop/bangla-karneval/frontend/js/admin_dashboard.js:397), [footer.js](C:/Users/tapan/Desktop/bangla-karneval/frontend/js/footer.js), and [admin_sponsors.js](C:/Users/tapan/Desktop/bangla-karneval/frontend/js/admin_sponsors.js).

3. **The Docker-mounted frontend is not configured as a Spring static resource location.** `resources.static-locations` is nested under `server`; the installed dependency identifies the applicable property as `spring.web.resources.static-locations`. The custom MVC handler only exposes `/uploads/**`. Consequently, the supplied configuration does not serve the frontend mounted at `/app/static`, or gallery files under that directory, as intended. This is a configuration finding; a fresh container startup was not executed. See [application.yml](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/resources/application.yml:46) and [WebMvcConfig.java](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/java/com/bangla/karneval/config/WebMvcConfig.java).

4. **Current-year gallery content is hidden.** Gallery CSS sets `.highlights-section` to `display: none`, and JavaScript excludes the current year from archive tabs. No code restores the highlights section. Therefore current-year highlights are hidden, and current-year non-highlight images have no public view either. Video uploads are offered in admin, but both the public renderer and lightbox always use an image element. See [gallery.css](C:/Users/tapan/Desktop/bangla-karneval/frontend/css/gallery.css:13) and [gallery.js](C:/Users/tapan/Desktop/bangla-karneval/frontend/js/gallery.js:62).

5. **Nested participant validation is not applied.** The additional-participant and performer-group lists lack cascading `@Valid`; the general registration list can also explicitly be null. A missing nested birth date can reach age calculation and cause an error; a future date can qualify as a free child. Performer counts are not checked against the actual list. Validate list values/elements and derive counts server-side. See [GeneralRegistrationRequest.java](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/java/com/bangla/karneval/dto/request/GeneralRegistrationRequest.java:30) and [PerformerRegistrationRequest.java](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/java/com/bangla/karneval/dto/request/PerformerRegistrationRequest.java:30).

6. **Updating contact details through the API can reset a confirmed payment.** The update controller constructs a new `Registration`, whose payment status defaults to `PENDING`. If an API client omits `paymentStatus`, the service still sees that default and overwrites the saved status. The current dashboard sends the status explicitly, so this affects partial API updates rather than its normal form submission. Use an update DTO with nullable fields. See [AdminRegistrationController.java](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/java/com/bangla/karneval/controller/AdminRegistrationController.java:44) and [RegistrationService.java](C:/Users/tapan/Desktop/bangla-karneval/backend/src/main/java/com/bangla/karneval/service/RegistrationService.java:93).

**Backend, database, and deployment concerns**

- Authorization currently means “has a valid token.” `@PreAuthorize` annotations are present but method security is not enabled, and URL rules use `.authenticated()` rather than an admin role requirement. Today login/register issue ADMIN tokens, so this is an unenforced role boundary, not an anonymous-access finding. Two JWT filter implementations also duplicate token processing. Password changes do not invalidate existing eight-hour tokens.
- CORS permits arbitrary origins with credentials but omits `PATCH`, used by sponsor toggles, visibility toggles, and marking messages read. Separate-origin frontends will fail those preflights. Same-origin deployment does not need these preflights.
- Uploads have no server-side image/content allowlist. Gallery filenames retain the supplied original filename rather than using a generated basename with a validated extension and normalized containment check. Sponsor filenames are sanitized, but uploaded content is still unrestricted. Gallery deletion removes only the database row, leaving the file accessible and consuming space. Sponsor replacement deletes the old file before the new file and database update have succeeded.
- Asynchronous email is requested before surrounding registration/status transactions commit. Messages may be sent for writes that later fail. Contact replies are marked answered before delivery succeeds, and reminders change to overdue before sending; a failed reminder is not selected again. There is no durable delivery status or retry queue. SMTP runtime failures are not handled by the `MessagingException` catch.
- Validation/error responses are inconsistent. Many expected failures throw generic runtime exceptions; enum conversion failures and invalid values can become server errors. Most string lengths are not validated against database limits. Price updates lack backend nonnegative validation. Public forms use `novalidate`, with incomplete replacement checks in registration and performer JavaScript.
- SQL and entity definitions differ: `registration_enabled` is absent from initialization SQL; Hibernate adds a nullable column without a database default, so the seeded row can yield a null interpreted as disabled. SQL uses BIGSERIAL for configuration ID while Java uses Integer. Admin-note columns have no entity fields. Performer deletion relies on the SQL cascade, which is not represented in JPA relationships for schemas created only by Hibernate.
- Production uses Hibernate `ddl-auto: update`; there are no versioned migrations. Docker initialization scripts run only for a new database volume, so editing those files does not upgrade existing databases. Re-running seed SQL manually duplicates sample events because there is no relevant unique constraint.
- “Current event” is hardcoded to 2026 in several backend services, dashboard logic, home requests, HTML, and email templates. Adding another gallery year does not switch the active event. Payment destination details are also hardcoded in HTML and email templates rather than configuration.
- Local development configuration uses a different database name and port from the supplied Compose host mapping. Upload/resource paths assume Linux `/app`. Terminal Maven initially selected Java 11 even though IntelliJ points to Java 17; explicitly selecting the installed Java 17 fixed compilation.
- No tests, README, Maven wrapper, migration tooling, or CI configuration are supplied. Registration/performer queries are unpaginated, and registration lists eagerly load additional participants. These become maintenance/performance concerns as data grows.

**Behavior to clarify when planning modifications**

The current configuration screen explicitly describes its registration controls as **button visibility**. They hide navigation links; direct form URLs and registration APIs remain usable. This is consistent with the present wording. If your plan is to close registration, server-side enforcement must be added.

Other decisions worth making in your plan: whether primary minors should pay, whether age is measured on event day, whether current-year non-highlight photos should be visible, which participant details admins need to inspect, whether payment instructions are final, and whether the application should support multiple active event years.

The existing controller/service/repository structure can support incremental changes. Address exposed credentials, unsafe HTML rendering, static-file configuration, validation, and payment-update correctness first; then implement the intended feature changes with focused tests for their affected flows.
